# 净图：纯前端传统算法图片去水印工具

版本：设计基线 v1.0  
形态：静态 HTML/CSS/JavaScript 单页应用；OpenCV.js + WebAssembly；不调用 AI、不需要业务后端。

## 1. 产品定位与关键决策

### 1.1 产品目标

让用户在浏览器里完成一条短而确定的工作流：**导入图片 → 标出水印 → 选择修复方式 → 对比结果 → 导出图片**。界面应像轻量修图工具，而不是专业图像软件：主要动作始终可见，参数数量受控，所有不可逆行为都能撤销或重新编辑。

### 1.2 明确不做什么

- 不依赖生成式 AI，不调用云端识别或修复服务。
- MVP 不自动“猜测”水印位置。自动定位并不是稳定的传统算法通用能力；由用户手动绘制蒙版可以覆盖文字、Logo、日期和重复水印中的选定片段，也便于修复失败后精准调整。
- 不承诺恢复被遮挡的原始内容。算法只能根据周边像素估算；大面积水印、脸部、文字、复杂建筑和高频纹理不保证自然。
- 不把复杂的 Photoshop 式能力放进首版，例如图层、贝塞尔路径、图章工具、曲线、批处理队列和云端账户。

### 1.3 核心技术决策

| 决策点 | 选择 | 原因 |
|---|---|---|
| 图像处理 | OpenCV.js + WebAssembly | 可使用成熟的经典 Inpainting 实现，无业务后端 |
| 默认算法 | Telea (`cv.INPAINT_TELEA`) | 默认简单、通常适合窄蒙版与小区域修复 |
| 备选算法 | Navier–Stokes (`cv.INPAINT_NS`) | 可在某些方向性边缘场景提供不同结果 |
| 蒙版输入 | 用户画笔 + 橡皮擦 | 用户直接控制修复位置，避免不可靠的“自动识别”承诺 |
| 蒙版边缘 | 可选形态学膨胀 | 减少水印抗锯齿边缘残留 |
| 前后对比 | 可拖动的分割线 | 同位置比较，视觉反馈直接 |
| 数据隐私 | 浏览器本地处理 | 用户图片不通过应用业务接口上传 |
| 大图计算 | 产品化版本使用 Web Worker | 避免同步 WASM 计算冻结界面；原型为保持单文件简单，计算放在主线程 |

注意：OpenCV.js 的不同预构建版本导出的 API 可能不同。部署时必须固定并测试所使用的版本，确认有 `cv.inpaint`、`cv.INPAINT_TELEA`、`cv.INPAINT_NS` 和 `photo` 模块；不要将浮动 CDN URL 当作永久稳定的生产依赖。官方说明了 OpenCV.js 的接入方式和 WASM 初始化机制，且 `inpaint` 的两种经典标志分别对应 Telea 和 Navier–Stokes。参考：

- OpenCV.js 接入与生命周期：[Using OpenCV.js](https://docs.opencv.org/5.0/js_tutorials/js_setup/js_usage/js_usage.html)
- `inpaint` 算法接口：[OpenCV Inpainting](https://docs.opencv.org/4.1.1/d7/d8b/group__photo__inpaint.html)

## 2. 用户、场景与成功标准

### 2.1 主要场景

1. 从风景照片中去除小段文字或细线水印。
2. 从纯色墙面、天空、地面等背景中修复小面积 Logo。
3. 对重复水印只选择需要清理的局部，而不是强行一次处理整张图。
4. 使用两个算法对比同一蒙版结果，选择视觉伪影较少的一版。

### 2.2 首版体验指标

- 新用户在首次打开页面后，能在 10 秒内找到导入入口。
- 用户导入图片后，无需阅读说明即可发现画笔、橡皮擦和修复按钮。
- 在修复前可以撤销/重做/清空标记；修复后可直接检查前后差异并继续编辑。
- 原图始终保留在内存中的独立画布中，不会被修复结果覆盖。
- 导出尺寸与原图像素尺寸一致；不因工作区预览缩放而降低输出分辨率。
- 加载失败、图片过大、无标记、修复异常等状态都给出具体反馈。

## 3. 信息架构与页面布局

### 3.1 单页工作台

1. **顶部栏**：品牌、隐私提示（“图片仅在本地处理”）、打开图片。
2. **标题与三步进度**：标记区域 → 修复画面 → 导出图片。步骤状态只用于指引，不作为阻塞式向导。
3. **中央画布区**：图片、蒙版覆盖层、修复结果层、画笔输入层彼此分离。
4. **右侧操作栏**：标记区域、修复方式、处理与导出三个分组。
5. **底部状态区**：当前状态、适应画布、原图/修复结果分割对比。
6. **Toast / 错误弹窗**：仅用于短反馈和需要用户关注的阻塞错误；非阻塞帮助使用行内提示。

### 3.2 视觉规范

- **整体**：浅灰背景、白色面板、低对比边框、大留白；强调色用靛紫，仅用于主要操作、选中态和修复蒙版。
- **层级**：页面标题 24–26 px；面板标题 13–14 px；控件标签 12 px；辅助说明 10–12 px。
- **按钮**：同一区域只有一个主按钮；危险操作（清空标记）采用次级样式并能撤销或恢复。
- **状态颜色**：绿色仅代表本地/完成/正常；橙色用于风险或高面积蒙版警告；红粉色用于待修复蒙版。不要把算法结果好坏仅通过颜色表达。
- **画布背景**：淡棋盘或点阵背景，帮助用户辨别透明区域和画布边界；图片本身不加滤镜或预览级压缩。
- **响应式**：宽屏采用“左侧画布 + 右侧设置”；窄屏设置栏移到画布下方。手机支持导入和基本涂抹，但大图精细操作优先面向桌面端。

## 4. 交互设计规格

### 4.1 导入

支持浏览器可解码的 PNG、JPEG、WebP、BMP；GIF 动画只考虑首帧（MVP 不以动画为目标），HEIC 不列入首版支持范围。

交互规则：
- 点击“打开图片 / 选择图片”、拖放到画布空状态均可导入。
- 新图成功导入后，清空旧蒙版、旧结果、撤销/重做栈和前后对比状态。
- 显示文件名、实际像素宽高和文件大小。
- 文件格式不支持、图片损坏、文件过大时保留当前工作并显示可读错误。
- 建议对大于 12 MP 的图像提示性能风险；不默认静默降采样输出。若未来增加快速预览缩略图，实际导出仍须回到原图尺寸重算。
- 浏览器解码后的画布像素遵循浏览器的 EXIF 方向处理；导出结果通常不保留原始 EXIF / GPS 元数据，文档需明确。

### 4.2 画笔和橡皮擦

- 默认工具为画笔，橡皮擦是同级工具按钮。
- 画笔用半透明洋红色覆盖层显示待修复范围；该颜色是操作提示，不会写进导出图。
- 用户按住鼠标/触摸拖动绘制连续笔迹，圆头、圆角连接。
- 画笔尺寸滑块以屏幕可见尺寸为交互单位，再按当前显示缩放换算为原图坐标；这样用户缩放预览后仍能掌控笔刷手感。
- 橡皮擦删除蒙版，不擦除原图像素。
- 所有笔迹以可重放的 Stroke 数据保存，而不是只保存最终蒙版；清空、撤销和重做都重绘整个蒙版。
- 首版可以不做触控笔压感；后续可增加压力影响笔刷宽度。

建议 Stroke 数据结构：

```ts
type Point = { x: number; y: number };
type Stroke = {
  mode: 'brush' | 'erase';
  size: number;          // 原图像素空间中的笔刷宽度
  points: Point[];       // 原图坐标，不能存屏幕坐标
  createdAt: number;
};
```

### 4.3 撤销 / 重做

- 每次完整的 pointerdown → pointerup 形成一个历史操作；不要为每个 pointermove 生成单独历史项。
- Ctrl/Cmd+Z 撤销；Ctrl/Cmd+Y 或 Ctrl/Cmd+Shift+Z 重做。
- 画笔尺寸变化不作为历史项；它只影响后续新笔迹。
- 清空蒙版后可以通过“撤销”恢复上一步（产品化版本建议将“清空蒙版”也写入 command history，而不是不可逆清空）。
- 当图片改变时清空历史栈。
- 对超长笔迹做点采样/简化，避免历史内存随每个 pointermove 无限制增长。

### 4.4 修复参数

| 参数 | 初始值 | 范围建议 | UX 规则 |
|---|---:|---:|---|
| 算法 | Telea | Telea / NS | 以通俗描述说明适用倾向，不称其为绝对优劣 |
| 修复半径 | 5 px | 2–15 px | 作用于原图像素；半径增大也可能模糊更多邻近纹理 |
| 蒙版扩展 | 2 px | 0–8 px | 对二值蒙版做椭圆核膨胀，主要用于清理半透明/抗锯齿边缘残留 |
| 画笔尺寸 | 24 px | 4–90 px（屏幕手感） | 涂抹覆盖略超出水印边缘，避免漏边 |

默认值是便于起步的经验值，不是对所有分辨率和场景都最优。产品化可以按原图较短边给出初始修复半径，但必须让用户看得见并能调整。

### 4.5 修复过程

1. 点击“开始修复”后禁用可能冲突的画布编辑动作，显示进度状态。
2. 若蒙版为空，不启动算法，并提示“先标记需要修复的区域”。
3. 生成二值蒙版，按用户设置选择是否膨胀。
4. 将 RGBA 原图转换为算法需要的三通道 8-bit 图像。
5. 调用 `cv.inpaint(src, mask, dst, radius, method)`。
6. 将输出转换回用于显示/导出的 RGBA 画布。
7. 切换到分割对比模式，用户拖动分割线检查修复边缘。
8. 保留原图和蒙版；支持“继续标记”后重新执行算法。
9. 若异常，释放临时 `cv.Mat`、恢复按钮状态，给出具体错误信息。

### 4.6 前后对比

- 修复成功后自动展示对比滑块。
- 左侧显示原图、右侧显示结果；分割线可拖动，键盘/范围滑块同步支持。
- 对比时隐藏蒙版覆盖层，避免把蒙版误认为输出内容。
- “继续标记”返回编辑状态；“导出图片”只读取修复结果画布。
- 如果想切换算法，保留蒙版，用户可以直接重新计算结果，不必重画。

### 4.7 导出

- 首版提供 PNG（无损，默认）和 JPEG（可调质量，建议 0.92–0.95）。
- 导出画布的 `width/height` 必须等于输入原图自然宽高。
- 文件名建议为 `{原文件名}_fixed.png` / `.jpg`。
- 导出成功触发浏览器下载，不调用服务端。
- 明确说明 JPEG 会重新压缩，PNG 通常更适合保留像素细节；原始元数据可能不保留。

## 5. 经典图像修复算法设计

### 5.1 为什么采用 Inpainting

水印不是纯粹的额外图层：很多情况下，原图已经与水印像素混合，不能直接用颜色阈值做减法。传统 Inpainting 的做法是标记损坏区域，再从周围已知像素估算缺失内容。它适用于局部、较窄的水印，但无法保证恢复真实被遮挡像素。

### 5.2 核心输入

- 原图 `I`：RGB 图像。
- 修复蒙版 `M`：单通道二值图；非零像素代表需要修复。
- 半径 `r`：修复时考虑周边像素的半径。
- 算法 `A`：Telea 或 Navier–Stokes。

数学上可写为：

\[
I_{out}=\operatorname{Inpaint}(I,M,r,A)
\]

### 5.3 推荐算法流水线

**步骤 A：构建二值蒙版**

```js
const rgbaMask = cv.matFromImageData(maskCanvasCtx.getImageData(0, 0, width, height));
const gray = new cv.Mat();
const binary = new cv.Mat();
cv.cvtColor(rgbaMask, gray, cv.COLOR_RGBA2GRAY);
cv.threshold(gray, binary, 1, 255, cv.THRESH_BINARY);
```

蒙版画布不与原图画布混用。UI 用半透明洋红展示蒙版，计算用隐藏的黑白/透明画布保存蒙版数据，避免导出时把标记颜色写入图像。

**步骤 B：蒙版扩展（可选）**

```js
const k = cv.getStructuringElement(
  cv.MORPH_ELLIPSE,
  new cv.Size(expand * 2 + 1, expand * 2 + 1)
);
cv.dilate(binary, dilated, k);
```

膨胀能覆盖文字边缘的抗锯齿和透明残色，但扩展过大也会扩大待猜测区域。默认应保持小值（例如 1–3 原图像素），并提供 0 作为关闭选项。

**步骤 C：准备源图像**

```js
const rgba = cv.matFromImageData(sourceCanvasCtx.getImageData(0, 0, width, height));
const rgb = new cv.Mat();
cv.cvtColor(rgba, rgb, cv.COLOR_RGBA2RGB);
```

确保输入类型、通道与具体 OpenCV.js 构建的 `inpaint` 约束一致。部分 API 构建只导出部分模块，因此启动时应检查能力，不要假设 CDN 一定包含 `inpaint`。

**步骤 D：执行修复**

```js
const output = new cv.Mat();
const method = selectedMethod === 'ns' ? cv.INPAINT_NS : cv.INPAINT_TELEA;
cv.inpaint(rgb, binary, output, radius, method);
```

**步骤 E：展示和释放资源**

将输出转换回画布可展示的 RGBA；随后 `delete()` 每个临时 `cv.Mat`。OpenCV.js 基于 WebAssembly 管理堆内存，若不主动释放矩阵，连续处理图片时可能逐渐耗尽内存。

### 5.4 不要把“颜色减法”当成通用算法

若水印叠加符合简化模型：

\[
C=\alpha W+(1-\alpha)B
\]

其中 `C` 为观测颜色、`W` 为水印颜色、`B` 为原图、`α` 为水印不透明度。只有在 `W` 和 `α` 已知且模型真实成立时，才可能反算 `B`。实际图片中水印透明度、混合模式和背景通常不明确，因此颜色减法对大多数普通图片不可靠；应将它视为针对固定水印模板的专项优化，不作为默认核心路线。

### 5.5 为什么不能承诺适用于所有水印

传统 Inpainting 主要依赖附近纹理和边缘传播。若遮挡区域很窄，附近像素能提供较好的约束；若区域宽、背景变化剧烈，算法缺少足够信息，只能做平滑或局部纹理延展。它并不了解“被遮住的是一只眼睛、一个字还是一块窗户”。这也是为什么交互设计必须允许用户分块标记、改变半径、比较算法和撤回结果。

## 6. 前端架构

建议逻辑分为五个职责模块，MVP 可先写在单页 HTML 中，后续再拆文件：

```text
src/
  app/             // 工作流状态、按钮、错误提示
  canvas/          // fit/zoom、坐标换算、原图/蒙版/结果图层
  history/         // stroke 命令、undo/redo
  repair/          // OpenCV 初始化、蒙版生成、inpaint、内存释放
  export/          // PNG/JPEG 导出
  styles/          // design tokens、布局、响应式规则
```

### 6.1 画布分层

1. `sourceCanvas`：原图，导入后只读；用于所有修复轮次。
2. `maskCanvas`：隐藏的二值蒙版数据层，只包含修复范围。
3. `maskOverlayCanvas`：UI 用半透明颜色展示蒙版。
4. `resultCanvas`：最近一次修复结果。
5. `paintSurface`：透明交互层，处理 pointer events 与笔刷坐标。

分层的原因是独立管理“输入数据、可视蒙版、结果、输入事件”，减少误导出的机会。任何时候都不应对原图执行覆盖式像素修改。

### 6.2 状态模型

```ts
type AppState = {
  source: HTMLImageElement | ImageBitmap | null;
  naturalWidth: number;
  naturalHeight: number;
  strokes: Stroke[];
  redoStack: Stroke[];
  selectedTool: 'brush' | 'erase';
  algorithm: 'telea' | 'ns';
  radius: number;
  maskExpand: number;
  resultReady: boolean;
  busy: boolean;
  comparePosition: number; // 0..100
};
```

关键约束：`source` 从不因修复而改变；`resultReady` 只有在成功生成并校验输出后才置为 true；编辑蒙版后必须标记结果为过期，避免用户导出旧结果。

### 6.3 Worker 与性能

原型在主线程执行 `cv.inpaint`，是为了让实现和交付简单；生产环境建议将 OpenCV WASM 及修复任务放入 Web Worker。Worker 消息仅传送 ImageData/可转移 ArrayBuffer、蒙版参数和任务 ID，不传 DOM 对象。

- 每个任务带递增 `jobId`，丢弃过期的异步结果，避免“用户切图后旧任务覆盖新图”。
- 导入新图时允许取消/忽略旧任务。
- 不要无条件复制多份 4K RGBA 数据。单个 3840×2160 RGBA 画布原始像素约 31.6 MiB；OpenCV 转换、蒙版、输出会带来多份额外内存。
- 高分辨率先提醒；产品化可先给低分辨率快速预览，但正式导出应在原图分辨率重算。
- 使用 `try/finally` 释放所有 `cv.Mat`，包括异常路径。
- 首屏可延迟加载 OpenCV.js：用户未导入图像前，不必先下载数 MB 的 WASM 依赖。

## 7. 错误与边界状态

| 场景 | 用户反馈 | 后续动作 |
|---|---|---|
| 没有图片 | 空状态与导入按钮 | 无 |
| 格式不支持 | “暂不支持该格式” | 保留当前画面 |
| 图片读取失败 | “图片读取失败，请换一张图片” | 允许重新导入 |
| 没有蒙版时点击修复 | 按钮禁用或行内提示 | 引导用户涂抹 |
| OpenCV 加载失败 | 明确提示依赖加载失败 | 重试；生产版提供本地静态依赖 |
| `cv.inpaint` 不存在 | 提示当前构建能力不完整 | 更换已验证构建，不静默用低质算法冒充 |
| 蒙版覆盖比例过大 | 非阻塞橙色提示 | 推荐分块修复；不强制阻止 |
| 处理耗时 | 处理中状态、按钮禁用 | 产品版 Worker 继续保持 UI 可用 |
| 修复异常 | 通用错误 + 可诊断日志 | 释放矩阵，回到可编辑状态 |
| 输出失败 | 显示导出失败 | 原结果仍可继续查看/重试 |

## 8. 安全、隐私与许可

- 不将图片、蒙版或结果发送到服务端；不要添加无说明的分析埋点或第三方图片请求。
- 若 OpenCV.js 通过 CDN 加载，浏览器会向该 CDN 请求代码/WASM 资产，但图片像素仍留在本地。对离线、企业或严格隐私场景，应随应用打包静态依赖，并配置 CSP。
- 保留原图直到用户关闭页面；不要在未确认情况下用处理结果覆盖原文件。
- 对版权标识、署名和来源标记，仅处理自己有权修改的图像。
- 产品发布前需复核 OpenCV 版本、第三方依赖及分发许可；锁定具体版本与哈希，记录升级日期。

## 9. 测试与验收

### 9.1 功能测试

- PNG/JPEG/WebP/BMP 导入、替换图片、损坏文件、超大文件。
- 画笔单点、连续拖动、慢速/快速描绘、指针离开画布、触摸输入。
- 画笔大小变化、橡皮擦、撤销、重做、清空、清空后撤销（完整版本）。
- Telea / NS 结果生成；蒙版扩展 0 和非 0；修复半径最小/最大值。
- 对比滑块 0%、50%、100%；修复后继续标记并重新生成。
- PNG/JPEG 导出尺寸与源图一致；导出时不包含蒙版颜色/对比线。
- 修复成功、OpenCV CDN 失败、`inpaint` API 缺失、矩阵异常后的内存释放和状态恢复。

### 9.2 视觉与交互验收

- 空状态一眼能看出“选择图片”是唯一首要入口。
- 导入后工具可见，不需要滚动才能找到“开始修复”。
- 选中的算法/工具有明显状态；所有按钮具备 hover、disabled 与键盘焦点状态。
- 蒙版颜色与原图有足够对比，但不能过度遮住水印和边缘。
- 处理结束后对比滑块明显出现；用户能立即理解哪边是原图、哪边是结果。
- 窄屏下控件不会横向溢出；画布操作区域优先保留空间。

### 9.3 质量评测集

建立一组有代表性的手工样例：

- 蓝天/墙面上的细字水印（低纹理）。
- 草地、树叶、砖墙上的 Logo（高频纹理）。
- 经过压缩的半透明水印（有抗锯齿边缘）。
- 斜线、细网格、建筑边缘穿过蒙版。
- 水印与脸部、文字或主体物重叠（预期提示效果有限，而不是要求还原成功）。

评价不只看“是否没有文字”，也看局部模糊、重复纹理、边缘断裂和颜色晕圈。算法对比应以同一个蒙版进行，避免把蒙版差异误判为算法差异。

## 10. 迭代路线

### MVP（当前原型）

- 单图导入；手动画笔/橡皮擦；撤销/重做；Telea/NS；半径与蒙版扩展；前后分割对比；PNG/JPEG 导出；本地运行。

### V1（质量与性能）

- Worker 计算、任务取消/去重、进度状态。
- 完整命令历史，包括清空、重画和参数前后版本。
- 拖拽缩放/平移画布、滚轮缩放、空格拖动画布。
- 更精准的画笔预览、快捷键帮助、JPEG 质量滑块。
- 质量评测图库、固定 OpenCV 构建与离线打包。

### V2（传统视觉增强，不使用 AI）

- 可选的颜色采样/阈值辅助蒙版，用于颜色规则明显且对比度高的固定水印。
- 针对重复图案的人工辅助选择、规则线/文字边界增强。
- 小范围 patch-based / exemplar-based 纹理填充作为额外实验算法，但只在明确的纹理场景下启用，并与 Inpaint 分开呈现。
- 多区域分次修复、结果版本历史、差异视图。

自动识别不建议在 MVP 做成默认按钮：单张照片中水印颜色、透明度、位置和背景都不固定，传统阈值算法的误检可能比手动标记更令用户困惑。

- `README.md`：启动方式和关键限制。
